starshipsuits project documentation

starshipsuits

Branding and public website for a fursuit-making studio. These are the working documents for the project: what the brand is, what it looks like, what the site contains, and how it gets built and shipped.

Where the project stands The domain is registered at Porkbun, the site is connected to Netlify and deploying from GitHub, and a coming-soon page is built in Direction A and ready to go live.

Two things stand between that page and the public internet: the Netlify site still has SSO protection inherited from the team account, so anonymous visitors get a 401; and DNS at Porkbun still points at the registrar's parking page rather than Netlify. See the DNS steps.

Direction A is provisional, not locked. The larger content questions - real prices, photography, terms - are unchanged and remain the long pole.

Fixed decisions

Settled, and not worth reopening without a reason:

DecisionChoiceWhy
Organisation nameStarship Suits Two words formally; starshipsuits as one word for the domain, handles and repository.
PaletteOrange, pink, light neutralClient-specified.
ThemeSpace / starshipClient-specified; carried by the name.
StackStatic HTML, CSS, JS - no framework A brochure and portfolio site has no server-side state. A framework would add a build step, a dependency tree, and a supply-chain surface for no functional gain.
Repositoryjohnzastrow/starshipsuits, private Private while it is a placeholder. Goes public when there is real content.
StagingGitHub Pages, currently disabled Pages is unavailable on private repositories on a free plan. Re-enables on going public.
Domainstarshipsuits.com at Porkbun Free WHOIS privacy, free email forwarding, ALIAS support, independent of the host. See the registrar comparison.
Production hostNetlify, deploying from this repository netlify.toml is committed with publish = "web" and the full security header set. See the DNS steps.
Publish directoryweb/ Only web/ is ever published. docs/ stays internal, enforced in both netlify.toml and the Pages workflow.
PlatformCustom build, not Wix Both reference studios use Wix. Custom wins on identity, speed and portability - but only because a developer is maintaining it. See the platform comparison.
